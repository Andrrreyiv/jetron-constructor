## 2. Что сделано и сверено

### 2.1. Скрипт прогона переписан под кадр-по-линейке

`scripts/run_normalize.py` был мёртв (звал удалённую константу `CANVAS`). Теперь он
идёт **в два прохода**, потому что высота кадра зависит от ВСЕХ расцветок линейки:

- `измерить(tasks)` — первый проход, собирает `ink_bbox` каждого исходника,
  возвращает `{индекс: bbox}` и список битых. Битый файл партию не роняет.
- `кадры_линеек(tasks, boxes)` — группирует bbox по линейке и зовёт `line_canvas`.
- В строку отчёта добавлено поле `canvas`, приёмка сверяет `size == canvas` **по линейке**,
  а не с глобальной константой.

⚠️ **Константу `CANVAS` в `report()` не возвращать.** Она и есть тот самый контракт
«добить всё до 900×1200», из-за которого под шортами рисовалась белая полоса.

**Инвариант высоты из приёмки УБРАН намеренно.** Внутри линейки высота формы законно
гуляет: это зазор поставщика между передом и задом и то, попали ли в кадр гетры и бутсы.
Ширину тоже не сверяем (пропорция формы 0.48..0.62). Сверяются **верх рамки** и **центр** —
зоны заданы долями ширины ХОЛСТА, поэтому уехавший центр уводит логотипы и номер.

## 3. 🔴 ЧТО ДЕЛАТЬ ДАЛЬШЕ — пересчёт зон (шаг 3 прежнего плана)

Это единственная незакрытая разработка. Сейчас на середине TDD: тест написан, красный,
реализации нет.

### Почему это обязательно

`zoneTemplate` в `src/config/mock-config.json` калиброван под холст 1200. Зоны — доли
0..1 **от холста**, а `zoneToRect` (`src/js/core/ZoneManager.js:80-87`) множит их на
**живой** размер Fabric-канваса. `CanvasView.setBackground` (`src/js/canvas.browser.js:38-62`)
вписывает фон по ширине и двигает высоту канваса под картинку — значит после перегона
холст у каждой линейки свой.

Числом: `chest_number` имеет `y = 0.455`, пиксельная цель 642.
`642/992 = 0.647` (Champion) против `642/1110 = 0.578` (Star). Одно общее число промахнётся
по Champion примерно на **68 px** — номер уедет вверх.

Порядок вызовов проверен грепом, а не памятью: `app.browser.js:1167` `await view.setBackground(...)`,
затем `:1171` `view.renderZones(zones)`. То есть доли резолвятся уже по подстроенной высоте.

### Шаг 3.1 — вернуть реализацию в `scripts/rewrite_catalog.py`

Тест уже лежит в `tests/test_rewrite_catalog.py::TestНаборыЗон`. Вставить **перед `def _слаг`**:

```python
# Высота кадра, на которой калиброван `zoneTemplate`: до 30.08 все 45 мокапов
# добивались белым до 1200, и доли зон меряли от неё.
ЭТАЛОННАЯ_ВЫСОТА = 1200


def наборы_зон(шаблон, кадры, эталон=ЭТАЛОННАЯ_ВЫСОТА):
    """Общий шаблон зон -> свой набор на каждую линейку.

    Кадр перестал быть общим: у Champion он 992 px, у Star 1110. Зона задана
    долей ОТ ХОЛСТА, поэтому один и тот же шаблон на разных линейках сажает
    номер в разные места формы — на Champion промах доходит до 68 px.

    Пересчёт чисто вертикальный: пиксели формы после перегона 30.08 не сдвинулись
    ни на один у всех 45 файлов (сверено с git), ушла только белая добивка снизу.
    Ширина кадра как была 900, так и осталась, поэтому `x` и `w` не трогаем.
    """
    return {
        линейка: [
            {
                **зона,
                "box": {
                    **зона["box"],
                    "y": round(зона["box"]["y"] * эталон / высота, 4),
                    "h": round(зона["box"]["h"] * эталон / высота, 4),
                },
            }
            for зона in шаблон
        ]
        for линейка, (_, высота) in кадры.items()
    }
```

⚠️ **Коллизия имён.** В `rewrite()` на строке 82 уже есть ЛОКАЛЬНАЯ переменная
`наборы_зон = {f["id"]: f["zoneSet"] ...}` (используется на строках 106-107 — она хранит
`zoneSet`, выставленные клиентом вручную). Её надо переименовать в `прежние_наборы`,
иначе новая функция затрётся.
